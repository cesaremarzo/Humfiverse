# Technical Architecture

## What is actually live today

Humfiverse's on-chain layer consists of two independent Solidity smart contracts, deployed and independently verified on **Ethereum Sepolia** (a public testnet — see [Current Status & Disclaimer](09-status-disclaimer.md) for exactly what "testnet" means for anyone reading this as a claim about real funds):

- **`HumfiverseCatalogueToken`** — an ERC-1155 contract that mints one token ID per catalogue or pre-production campaign into a platform-held pool, and controls every path tokens can leave that pool: a fixed-price public `buy()` for already-monetized catalogues, and an authorized-caller `releaseFromPool()` that the milestone-escrow contract calls atomically when a pre-production contribution is confirmed. Each token ID also carries its track's title, artist name, and — when the artist has uploaded one — a link to the actual audio file, pinned to IPFS, all readable directly from the contract by anyone, on a block explorer, independent of Humfiverse's own website.
- **`HumfiverseMilestoneEscrow`** — holds contributed ETH for pre-production campaigns and releases it in tranches, gated on a specific and deliberate rule: a milestone pays out only once **both** the campaign's artist and its assigned studio confirm, from their own wallets, that it genuinely happened. There is no function anywhere in this contract — including for Humfiverse's own operator role — that can release a tranche on one party's say-so. If the two sides disagree, funds simply stay locked; there is no arbitration path, on purpose (see the governance chapter for why giving Humfiverse discretionary approval power was a real legal exposure this design specifically closes off).

A third contract, `HumfiverseMarketplace`, implementing peer-to-peer resale of already-purchased tokens with a 1% platform fee taken from the token side of the trade, is written and fully tested but not yet deployed — resale is currently simulated in the application layer while the underlying compliance question (see [Legal & Regulatory Structure](05-legal-structure.md)) is worked through. Both live contracts have gone through 71 passing automated tests covering minting, pool accounting, dual-confirmation release, refund math, and access control — this is test coverage, not a third-party security audit, and the two should not be conflated (see [Risk Factors](08-risk-factors.md)).

## Why an EVM chain, and why Sepolia specifically

An EVM-compatible chain was the pragmatic starting choice given tooling maturity and direct precedent — anotherblock, the closest existing comparable in this exact space, runs on Ethereum and its L2 Optimism. Humfiverse's pilot deployment sits on Ethereum Sepolia rather than a Layer 2, a practical choice for a pre-revenue pilot moving no real value yet: Sepolia's public faucets make testnet ETH easy to obtain for development and demonstration, which mattered more at this stage than the lower transaction costs an L2 would offer once real royalty payouts are frequent enough for that to matter. That tradeoff is explicitly revisited before any mainnet deployment — the architecture does not assume Sepolia is the permanent home for this system, only that it is the right place to prove the mechanism first.

## The hardest problem here is not the smart contract

The genuinely difficult part of this system is not minting a token or writing an escrow contract — both are well-understood patterns. It is everything that has to happen *before* a token exists (proving a royalty right is real, unencumbered, and worth what it claims) and everything that has to happen for royalty income to *become* an on-chain event at all.

Royalty income does not arrive on-chain natively. A DSP or a collecting society pays into a traditional bank or collection account, and someone — Humfiverse, a royalty administrator, or both — has to confirm that payment happened and submit that confirmation on-chain before a distribution contract can pay it out to token holders. In this system's current design, that confirmation step is an **attested trust point**: a designated, named party signs off that a royalty payment was received, rather than a fully decentralized oracle network verifying it trustlessly. This is stated plainly rather than glossed over, because overstating decentralization here would be dishonest about exactly the piece of the system investors most need to understand correctly: today, "on-chain" means the *distribution and custody* of confirmed royalty income is verifiable and automated; it does not yet mean the *confirmation itself* is trustless. A path toward a more decentralized attestation — a multisig of the platform and an independent royalty administrator, and eventually a broader oracle network — is a planned evolution, not a claim made about the system as it stands today.

## What the local database is, and is not

Humfiverse's backend maintains a conventional database (SQLite in development, a hosted libSQL database in production) that indexes on-chain state for fast reads — which catalogues exist, their current pool balances, escrow campaign status. This index is explicitly a cache, not a source of truth: every value it holds is re-derivable from the chain itself, and the application is built to self-heal that cache from real on-chain events whenever it is found to be stale or wiped. Nothing an investor should rely on — a token balance, a campaign's funding status, a milestone's confirmation state — exists *only* in this database; it always exists on-chain first; the database exists so the application does not have to re-scan the entire blockchain's history on every page load.

## Publicly verifiable, on purpose

Both live contracts are verified on Sepolia's block explorer, meaning their actual Solidity source — not just compiled bytecode — is readable by anyone, and every function call and event they process is decoded in plain terms rather than raw hexadecimal. Every asset listed on Humfiverse links directly to its own contract's explorer page and, for pre-production campaigns, to its escrow contract's page as well. This is a deliberate design commitment, not a feature added for marketing: the entire premise of tokenizing a claim on a cash flow is that the claim's terms are checkable by the person holding it, independent of Humfiverse's own continued existence or good behavior.
